Why I Chose Option C (Fully Snowflake-Native)

1. Security & Governance

  • Data never leaves Snowflake. No network egress, no third-party data processing agreements needed.
  • No API keys to store, rotate, or accidentally leak in git. Zero secrets management overhead.
  • Snowflake's built-in RBAC controls who can access the agent and underlying data.
  • For a regulated industry (which the interview may ask about), this is table-stakes compliance.

2. Reduced Operational Complexity

  • No external infrastructure to maintain. No Lambda functions, no API gateways, no vector databases, no container orchestration.
  • No version conflicts between LangChain/OpenAI SDK updates.
  • No billing surprises from external token usage (Snowflake credits are predictable).
  • Deployment = SQL DDL. No Docker, no CI/CD pipelines for external services.

3. Built-in Capabilities I Get For Free

  • Cortex Analyst handles text-to-SQL with semantic view context (I don't build a SQL generator).
  • Cortex Agent handles multi-tool routing (I don't build a router/planner).
  • Built-in guardrails for content safety and grounding (I don't build a safety filter).
  • Structured responses with text + table data (I don't build response parsing).
  • Session auth in SiS means no OAuth flows, no token refresh, no credential storage.

4. Platform Alignment

  • This is a Snowflake Applied AI role. Demonstrating mastery of Snowflake's native AI stack directly shows I can work within the platform's capabilities and push them to their limits.
  • I'm building WITH the platform, not around it.
What I gave up: Streaming responses (SiS doesn't support it yet for agent calls), model choice flexibility (locked to "auto"), longer processing budgets. These are acceptable tradeoffs for the security, simplicity, and governance gains.

Why Semantic View Quality Is Everything

The LLM is only as good as the context it receives. Cortex Analyst doesn't "know" census data. It reads the semantic view definition and generates SQL based on what it sees. If the semantic view says comment='Estimated count' with no guidance on filters, the LLM will SUM everything and produce wrong numbers. My ai_sql_generation instructions prevent this: "CRITICAL: For total population ALWAYS filter FIELD_ID='B01001e1'"

VQRs: The Golden Path

Verified Query Representations (VQRs) are pre-validated SQL that Cortex Analyst can use directly when a question matches:

Without VQR (LLM generates from scratch)

  • LLM must infer correct FIELD_ID filters
  • May pick wrong aggregation (SUM vs AVG)
  • ~70-80% accuracy on complex queries
  • Takes more tokens/time to reason

With VQR (uses verified SQL)

  • Exact SQL already proven correct
  • Near 100% accuracy for matching questions
  • Faster (less reasoning needed)
  • Acts as few-shot examples for similar questions

4. Data Flow: Raw Census to Agent-Ready

The Problem: Cryptic Coded Data

-- Raw table has 200+ coded columns. What does B01001e10 mean?
SELECT "B01001e1", "B01001e2", ... "B01001e49"
FROM US_OPEN_CENSUSDATA.PUBLIC."2019_CBG_B01"
-- Answer: "Male, 22 to 24 years" — but only metadata knows this

The Solution: UNPIVOT + Metadata JOIN (Repeated 24x)

-- STEP 1: UNPIVOT coded columns into rows (wide → tall)
FROM "2019_CBG_B01"
  UNPIVOT(col_value FOR col_name IN ("B01001e1", "B01001e2", ... "B01001e49"))

-- STEP 2: JOIN metadata for human-readable labels
LEFT JOIN "2019_METADATA_CBG_FIELD_DESCRIPTIONS" m
  ON LOWER(m.TABLE_ID) = LOWER(col_name)
  -- Gives: TABLE_TITLE='Sex By Age', SEX='Male', AGE_GROUP='22 to 24 years'

-- STEP 3: JOIN FIPS codes for geographic context
LEFT JOIN "2019_METADATA_CBG_FIPS_CODES" f
  ON SUBSTR(CENSUS_BLOCK_GROUP, 1, 2) = f.STATE_FIPS
  AND SUBSTR(CENSUS_BLOCK_GROUP, 3, 3) = f.COUNTY_FIPS
  -- Gives: STATE='CA', COUNTY='Los Angeles County'

-- STEP 4: Filter estimates only (exclude margins of error)
WHERE m.FIELD_LEVEL_1 = 'Estimate'

7. Semantic Layer Design (Where the Intelligence Lives)

Each semantic view has 7 annotation types. Together they form the "brain" that makes SQL generation accurate:

AnnotationPurposeExample
TABLESMaps alias to base view + business commentPOVERTY as V_POVERTY comment='Poverty status at Block Group level'
FACTSIdentifies numeric measures + meaningVALUE comment='Count of people OR dollar amount for deficit tables'
DIMENSIONSCategorical columns with SYNONYMS + SAMPLE_VALUES + IS_ENUMSTATE with synonyms=('us state') sample_values('CA','TX') is_enum

What IS_ENUM Does (Critical for Accuracy)

IS_ENUM tells Cortex Analyst that a column has a fixed, finite set of valid values (like a dropdown), not free-text or continuous numbers.

Without IS_ENUMWith IS_ENUM
LLM treats STATE as free-text, might generate WHERE state = 'California' (WRONG — data uses 2-letter codes)LLM knows STATE has a closed set, checks sample_values, generates WHERE state = 'CA' (CORRECT)
LLM might try WHERE sex = 'M' or WHERE sex = 'male'LLM knows only 'Male' and 'Female' are valid, uses exact casing
LLM might use LIKE patterns or partial matchingLLM uses exact = equality with known valid values

Columns marked IS_ENUM in my views: STATE (52 values), SEX (Male/Female), AGE_GROUP (23 buckets), ESTIMATE_TYPE (always "Estimate"), TABLE_TITLE, CATEGORY_1, CATEGORY_2 (race groups, income brackets, marital status, etc.)

Impact: Without IS_ENUM, the LLM guesses filter values and gets them wrong ~30% of the time. With IS_ENUM + SAMPLE_VALUES, it picks from the known valid set — eliminating an entire class of "wrong value" errors.

Concrete Example: Full Semantic View (SV_INCOME)

This shows how all 7 annotations work together for one view:

create or replace semantic view SV_INCOME
  -- TABLES: maps alias to physical view
  tables (
    INCOME as CENSUS_INTELLIGENCE_DB.PUBLIC.V_INCOME
      comment='US Census 2019 ACS household income at Block Group level'
  )
  -- FACTS: the numeric measure column
  facts (
    INCOME.VALUE as VALUE
      comment='Household count OR dollar amount for median/per-capita tables'
      sample_values ('0', '50', '500', '65000', '150000')
  )
  -- DIMENSIONS: categorical/descriptive columns
  dimensions (
    INCOME.STATE as STATE
      with synonyms=('us state','state name')
      comment='US state 2-letter abbreviation'
      sample_values ('CA', 'TX', 'NY', 'FL', 'IL', 'PA')
      is_enum,
    INCOME.FIELD_ID as FIELD_ID
      comment='B19001e1=Total households. B19013e1=Median HH income. B19301e1=Per capita income.'
      sample_values ('B19001e1', 'B19013e1', 'B19301e1'),
    INCOME.CATEGORY_2 as CATEGORY_2
      with synonyms=('income bracket','income range')
      comment='Income bracket for count table. NULL for median rows.'
      sample_values ('Less than $10 000', '$50 000 to $59 999', '$200 000 or more')
      is_enum
  )
  -- METRICS: pre-defined aggregation with warning
  metrics (
    INCOME.TOTAL_HOUSEHOLDS as SUM(VALUE)
      comment='ALWAYS use FIELD_ID filter. For median income use AVG not SUM.'
  )
  -- AI_SQL_GENERATION: critical instructions for the LLM
  ai_sql_generation 'CRITICAL: B19013e1=Median household income (use AVG for state/county).
    Do NOT SUM median income rows—use AVG. B19001e1=Total household count.'
  -- AI_QUESTION_CATEGORIZATION: routing hints
  ai_question_categorization 'Answers: household income, median income, per capita income.
    REJECT: race, age, education, commuting, poverty.'
  -- AI_VERIFIED_QUERIES: golden SQL examples
  ai_verified_queries (
    MEDIAN_INCOME_BY_STATE AS (
      QUESTION 'What is the average median household income by state?'
      VERIFIED_BY '(STEWARD = venu)'
      ONBOARDING_QUESTION true
      SQL 'SELECT income.state,
             AVG(income.value) AS avg_median_household_income
           FROM V_INCOME AS income
           WHERE income.field_id = ''B19013e1'' AND income.value > 0
           GROUP BY income.state
           ORDER BY avg_median_household_income DESC')
  );

Notice: The ai_sql_generation says "use AVG not SUM for medians" — this single instruction prevents the #1 error class for income queries (SUM of medians is mathematically meaningless).

Example: How VQR Prevents Wrong SQL

User asks: "Which states have the highest median household income?"

Without VQR (LLM guesses)

-- WRONG: SUM of median values
SELECT state,
  SUM(value) AS income
FROM V_INCOME
WHERE field_id = 'B19013e1'
GROUP BY state
ORDER BY income DESC

Returns millions (summed medians across block groups) — meaningless number.

With VQR (uses verified SQL)

-- CORRECT: AVG of median values
SELECT state,
  AVG(value) AS avg_median_income
FROM V_INCOME
WHERE field_id = 'B19013e1'
  AND value > 0
GROUP BY state
ORDER BY avg_median_income DESC

Returns ~$65K-$85K per state — correct weighted average of block-group medians.

Example: How ai_question_categorization Routes Questions

When user asks "What is the gender pay gap by state?", the agent reads all 24 tool descriptions:

Tool: query_income → "Queries household income. NOT for individual earnings."
  → REJECT (this is about individual earnings, not household income)

Tool: query_earnings → "Individual earnings by sex. B20002e2=Male median, B20002e3=Female median."
  → MATCH (gender + earnings = this tool)

Tool: query_education → "Educational attainment. REJECT: income, earnings..."
  → REJECT (explicitly excludes earnings)

The "NOT for individual earnings" in query_income and the explicit match in query_earnings guide the agent to the correct tool. Without these hints, the agent might route to SV_INCOME (wrong — that's household-level, not individual).

My Iterative Testing Workflow

1. Write semantic view DDL (annotations, VQRs, sql_generation hints)
2. Deploy: CREATE OR REPLACE SEMANTIC VIEW SV_POVERTY ...
3. Test directly: CoCo call_cortex_analyst with 5-10 questions → verify SQL correctness
4. Validate VQRs compile: SYSTEM$CORTEX_ANALYST_SVA_TOOL('validate_verified_queries', ...)
5. Run native evaluation: EXECUTE_AI_EVALUATION → sql_correctness score
6. Fix issues: adjust ai_sql_generation hints, add VQRs for failing patterns
7. Repeat 3-6 until accuracy is acceptable
8. THEN add to agent as a tool (confident it works independently)

Why this matters: If a semantic view produces wrong SQL when tested alone, it will produce wrong SQL inside the agent too. Testing at the view level isolates data layer issues from agent orchestration issues. I can fix annotations without touching the agent spec.

Deep Dive: How ai_sql_generation, ai_question_categorization, and VQRs Work

ai_sql_generation — The LLM's SQL Writing Instructions

Purpose: Explicit rules about HOW to write SQL for this specific view. Without it, the LLM must guess — and it guesses wrong on domain-specific patterns.

From Snowflake docs: "For instructions on how to generate the SQL statement, use the AI_SQL_GENERATION clause."

Census example (SV_INCOME):

ai_sql_generation 'CRITICAL: B19013e1=Median household income (use AVG for state/county).
  Do NOT SUM median income rows—use AVG. B19001e1=Total household count.'

What this prevents:

Without ai_sql_generationWith ai_sql_generation
LLM generates SUM(value) WHERE field_id='B19013e1' → Returns $14 billion (sum of all medians — meaningless)LLM generates AVG(value) WHERE field_id='B19013e1' → Returns $65,000 (correct)
LLM doesn't know which FIELD_ID to use for "total population" — scans all 49 fields causing double-countingLLM reads "B01001e1=Total Pop" and immediately filters correctly
LLM generates SUM(value) without any filter → returns garbage (sums estimates + medians + aggregates together)Instruction says "ALWAYS pair with FIELD_ID filter" → LLM adds WHERE clause

Key insight: This is like writing precise instructions for a contractor who has never seen your house. The more explicit, the fewer mistakes. A single missing hint (like "use AVG not SUM for medians") can cause EVERY income query to return wrong numbers.

ai_question_categorization — The Routing Classifier

Purpose: Tells the Cortex Agent WHEN to route a question to this view and when to REJECT it. This prevents cross-domain misrouting.

From Snowflake docs: "For instructions on how to classify questions and prompt for additional information, use the AI_QUESTION_CATEGORIZATION clause."

Census example (SV_POVERTY):

ai_question_categorization 'Answers: poverty rate, poverty status, people below poverty line,
  poverty by geography, income deficit, poverty by family type.
  REJECT: income distribution, race, education, housing, commuting, age, sex.'

How the agent uses this for routing:

User: "What is the median household income by state?"

Agent reads 24 tool descriptions:
  query_poverty → ai_question_categorization says "REJECT: income distribution"
    → SKIP (income is explicitly rejected)
  query_income → ai_question_categorization says "Answers: household income, median income"
    → MATCH! Route here.
  query_earnings → says "NOT for household income"
    → SKIP

Without explicit REJECT lists: "poverty rate" and "income" are semantically close — both involve money. The agent might route income questions to the poverty view (which would fail because poverty views don't have median income data). The REJECT list prevents this.

ai_verified_queries (VQRs) — Golden SQL + Few-Shot Examples + Regression Tests

Purpose: Three roles simultaneously:

  1. Accuracy booster — If question matches a VQR, Analyst uses that SQL directly (near-100% correct)
  2. Few-shot examples — For similar questions, VQRs teach the LLM correct patterns (which FIELD_IDs, aggregation, filters)
  3. Regression tests — During evaluation, VQRs are temporarily removed from the view and used as ground truth to measure accuracy

From Snowflake docs: "When you select verified queries for an evaluation run, Cortex Analyst creates a temporary copy of your semantic view with those selected queries removed." This ensures the evaluation measures real SQL generation ability, not memorization.

Census example (SV_EMPLOYMENT):

UNEMPLOYMENT_BY_STATE AS (
  QUESTION 'What is the unemployment rate by state?'
  VERIFIED_BY '(STEWARD = venu)'
  ONBOARDING_QUESTION true
  SQL 'SELECT employment.state,
         ROUND(100.0 * SUM(CASE WHEN employment.field_id = ''B23025e5'' ...)
         / NULLIF(SUM(CASE WHEN employment.field_id = ''B23025e2'' ...), 0), 2)
         AS unemployment_rate_pct
       FROM V_EMPLOYMENT ...'
)

Runtime behavior:

ScenarioWhat Happens
User asks exact VQR questionAnalyst uses golden SQL directly → 100% correct
User asks similar question ("unemployment in California?")Analyst adapts VQR pattern (adds WHERE state='CA') → ~90% correct
User asks related but different ("labor force participation?")Analyst uses VQR as template for FIELD_ID patterns → moderate accuracy
User asks unrelated ("median rent?")VQR doesn't apply; view rejected by categorization; different tool used

ONBOARDING_QUESTION true — means this question appears as a suggestion in CoWork ("Try asking: What is the unemployment rate by state?"). Guides users toward questions the system handles best.

When the Skill Gets Used

The agent consults the skill when it needs domain knowledge that isn't in the orchestration instructions or semantic view definitions. Examples:

  • "What does poverty rate mean?" → Agent looks up the skill's BUSINESS DEFINITIONS section for the formula: below-poverty / total population for poverty determination
  • "What's the difference between income and earnings?" → Skill defines: income = household-level (B19xxx), earnings = individual-level (B20xxx)
  • "Is Hispanic a race?" → Skill states: "Hispanic/Latino is an ETHNICITY, not a race. A person can be Hispanic AND White/Black/Asian."
  • "Why is the unemployment rate different from what I expected?" → Skill explains: "Unemployment rate = Unemployed / In labor force (NOT total population). Only counts people actively seeking work."
  • Complex derived metrics → Skill provides exact formulas: gender pay gap, homeownership rate, SNAP rate, college degree rate

What the Skill Provides That Orchestration/Response Can't

Too large for orchestration instructions:

  • Full FIELD_ID reference tables (50+ field codes mapped to descriptions)
  • Derived metric formulas with exact SQL patterns
  • Data quality notes (when to trust small-population estimates)
  • Universe definitions per table (education = 25+, employment = 16+, marital = 15+)

What orchestration instructions handle instead:

  • Persona ("You are a census data analyst")
  • Security guardrails (refuse prompt injection)
  • Communication style (lead with insight, no SQL)
  • Geography defaults (nationwide unless specified)

8. Streamlit UI Architecture

Smart Follow-up Rewriting

Detects short confirmations ("yes", "go ahead", "sure") and rewrites them into standalone questions by extracting the agent's last suggestion.

Why: "yes" with full context wastes 20s+ of the 60s budget on context parsing.

How: Regex extracts "Want to see..." / "Would you like..." from last agent message, combines with user intent.

Concrete example:

Agent: "Mississippi has the highest poverty rate at 19.7%.
Would you like to see the breakdown by age group?"

User types: "yes"

→ Regex finds: "Would you like to see the breakdown by age group?"
→ Rewrites to: "Show me the breakdown by age group — yes"
→ Agent receives standalone question, no context parsing needed
→ Responds in 15s instead of 35s

History Limiting (Last 4 Messages)

Only sends most recent 4 messages (2 user + 2 assistant) to the agent.

Why: Reduces token consumption, keeps agent focused, faster processing.

Full history: Still stored in CHAT_HISTORY table for sidebar display + reload.

Background Threading + Progress

Agent runs in threading.Thread(daemon=True) while main thread animates 6-step progress bar.

Why: SiS doesn't support async. Threading is the only way to keep UI responsive during 10-40s agent calls.

Persistent Chat History

Every message → INSERT into CHAT_HISTORY (CONVERSATION_ID, USER_NAME, SEQ, ROLE, CONTENT).

Why: Survives page refresh. Reviewers can test, close, come back. Past conversations loadable from sidebar.

CoWork Thread Flow (Server-Managed)

1. First message: CoWork creates a thread_id, sends with parent_message_id: 0
2. Agent responds: API streams metadata events:
   event: metadata → {"role":"user", "message_id": 123}
   event: metadata → {"role":"assistant", "message_id": 456}
3. Follow-up: CoWork sends next question with parent_message_id: 456
   → Server reconstructs: 0 → 123(user) → 456(assistant) → 789(user) → ...
4. Long threads: Cortex auto-compacts older turns into a summary message
   → Agent sees: [summary of turns 1-10] + [turn 11] + [turn 12] + [current]

Streamlit Multi-Turn Flow (Client-Managed)

1. Full history stored in session_state.messages (never trimmed client-side)
2. Every message persisted to CHAT_HISTORY table (survives refresh)
3. Only LAST 4 messages sent to agent via DATA_AGENT_RUN() (stateless SQL call)
4. Short replies ("yes") → smart rewriting extracts agent's last suggestion
5. Agent resolves "that state" / "what about income?" from the 4-message window

Why the difference: DATA_AGENT_RUN() via session.sql() is stateless — it doesn't use Threads. I had to manually implement context management. CoWork uses the REST API with Threads, where Snowflake handles state server-side.

16. What I Would Improve With More Time

A. Merge Semantic Views (24 → Fewer)

Why: 24 tools means the agent's routing LLM must read 24 descriptions to pick the right one. This takes tokens and time. Some views are closely related and could be merged.

How I would approach it:

  • Candidate merges: SV_RACE + SV_RACE_DETAILED + SV_HISPANIC_ORIGIN → SV_RACE_ETHNICITY (3→1)
  • Candidate merges: SV_EDUCATION + SV_EDUCATION_BY_SEX → SV_EDUCATION (2→1)
  • Candidate merges: SV_INCOME + SV_EARNINGS → SV_INCOME_EARNINGS (2→1)
  • Target: 24 → 12-15 views, reducing routing complexity by 40%
  • Risk: Merged views have more columns, which can confuse Cortex Analyst. Need to compensate with stronger ai_sql_generation instructions and more VQRs.
  • Method: Monitor tool usage distribution first (which views are used together), then merge those. Use CoCo's semantic-view skill evaluation to verify no accuracy regression after merging.

B. Agent Timeout Issues (>60 Second Queries)

Problem: Some queries hit the 60s budget — especially cross-domain questions that trigger multiple tool calls, or aggregations over all 220K block groups with complex JOINs.

Root causes identified:

  • Agent selecting wrong tool first → retries with correct tool (wastes 20-30s)
  • Complex multi-step questions that need data from 2+ semantic views
  • Large UNPIVOT scans when no FIELD_ID filter is applied (scans millions of rows)

Solutions I would implement:

  • Pre-aggregated state-level summary views: Create V_STATE_SUMMARY_* views that pre-compute common state-level metrics. Semantic views point to these for state-level questions, avoiding block-group-level scans.
  • Better tool descriptions: More explicit routing hints in tool descriptions to reduce misroutes. Add "NOT for..." exclusions.
  • More VQRs: Every VQR that matches saves the LLM from reasoning about SQL generation — immediate speedup.
  • Clustering keys: Add clustering on STATE and FIELD_ID columns in base views for partition pruning.
  • Query timeout detection: Already implemented in the app — shows helpful suggestion to simplify the question. But preventing the timeout is better than recovering from it.

C. Evaluations & Aggressive Validation

Current state: 40-question golden dataset, eval config written, TSA score of 81.6%. Manual testing across all 24 domains.

What I would do with more time:

  • Run Snowflake Native Evaluations: Use sql_correctness metric with 100+ test questions. Measure precision/recall per semantic view. Build regression suite.
  • Expand VQR coverage: From ~30 to 100+ verified queries. Cover edge cases: county-level, multi-step, cross-domain, percentage calculations.
  • Tool selection accuracy metric: Track whether the agent routes to the correct SV. Misroutes are the #1 cause of wrong answers.
  • Latency tracking: Measure end-to-end time per query, time in SQL generation vs execution. Identify which views are slowest.

  • Adversarial testing: Systematic prompt injection, SQL injection, boundary cases. Currently have 22 guardrail tests — would expand to 50+.

What is Multi-Tenancy?

Tenant = an independent customer/organization that uses the same application but must only see their own data. Multi-tenancy means serving 50 different organizations from a single deployment without any tenant seeing another's data.

Census example: Imagine 50 state government agencies each use this agent, but Oregon's agency should only see Oregon data, California's should only see California data — same agent, same infrastructure, different data boundaries.

Three Multi-Tenancy Approaches in Snowflake

ApproachHow It WorksBest ForCensus Example
Option A: Shared + Row Access PoliciesOne database, one agent, one set of views. Row Access Policy filters data per tenant's role.Low cost, many tenants, same schema, moderate isolationAll 50 states share the same views. RAP ensures Oregon only sees STATE='OR' rows.
Option B: Database-per-Tenant (Zero-Copy Clone)Clone database for each tenant. Each gets their own agent + views + data.Regulated industries, strong isolation, custom data per tenantEach state agency gets a cloned DB with their state's data pre-filtered.
Option C: Schema-per-TenantOne database, separate schema per tenant. Views/agent isolated per schema.Moderate isolation, shared administration, tenant-specific SVsCENSUS_DB.OREGON, CENSUS_DB.CALIFORNIA — each has their own views tuned to local needs.

Option A Deep-Dive: RBAC + Row Access Policies (Recommended for This Use Case)

-- STEP 1: Create a role per tenant
CREATE ROLE TENANT_OREGON;
CREATE ROLE TENANT_CALIFORNIA;
CREATE ROLE TENANT_TEXAS;

-- STEP 2: Grant access to the shared objects
GRANT USAGE ON DATABASE CENSUS_INTELLIGENCE_DB TO ROLE TENANT_OREGON;
GRANT USAGE ON SCHEMA CENSUS_INTELLIGENCE_DB.PUBLIC TO ROLE TENANT_OREGON;
GRANT SELECT ON ALL VIEWS IN SCHEMA CENSUS_INTELLIGENCE_DB.PUBLIC TO ROLE TENANT_OREGON;
GRANT SELECT, REFERENCES ON ALL SEMANTIC VIEWS IN SCHEMA CENSUS_INTELLIGENCE_DB.PUBLIC TO ROLE TENANT_OREGON;
-- (repeat for each tenant role)

-- STEP 3: Create a mapping table (tenant → state filter)
CREATE TABLE TENANT_STATE_MAPPING (
    TENANT_ROLE VARCHAR,
    ALLOWED_STATES ARRAY
);
INSERT INTO TENANT_STATE_MAPPING VALUES
    ('TENANT_OREGON', ARRAY_CONSTRUCT('OR')),
    ('TENANT_CALIFORNIA', ARRAY_CONSTRUCT('CA')),
    ('TENANT_TEXAS', ARRAY_CONSTRUCT('TX'));
-- Some tenants might see multiple states (regional agency):
INSERT INTO TENANT_STATE_MAPPING VALUES
    ('TENANT_SOUTHEAST', ARRAY_CONSTRUCT('FL', 'GA', 'AL', 'MS', 'LA', 'SC', 'NC'));

-- STEP 4: Create Row Access Policy
CREATE OR REPLACE ROW ACCESS POLICY tenant_state_filter
AS (state_value VARCHAR) RETURNS BOOLEAN ->
    CURRENT_ROLE() = 'SYSADMIN'  -- admins see everything
    OR EXISTS (
        SELECT 1 FROM TENANT_STATE_MAPPING
        WHERE TENANT_ROLE = CURRENT_ROLE()
          AND ARRAY_CONTAINS(state_value::VARIANT, ALLOWED_STATES)
    );

-- STEP 5: Apply RAP to every base view's STATE column
ALTER VIEW V_POVERTY ADD ROW ACCESS POLICY tenant_state_filter ON (STATE);
ALTER VIEW V_INCOME ADD ROW ACCESS POLICY tenant_state_filter ON (STATE);
ALTER VIEW V_EDUCATION ADD ROW ACCESS POLICY tenant_state_filter ON (STATE);
-- ... apply to all 24 views

-- STEP 6: Create users and assign tenant roles
CREATE USER oregon_analyst PASSWORD = '***' DEFAULT_ROLE = TENANT_OREGON;
GRANT ROLE TENANT_OREGON TO USER oregon_analyst;
GRANT DATABASE ROLE SNOWFLAKE.CORTEX_USER TO ROLE TENANT_OREGON;

Result: When Oregon's user asks "What is the poverty rate by state?", the agent calls the same semantic view, same SQL is generated, but the Row Access Policy silently filters to only STATE='OR' rows. They never see other states' data. Zero code changes to the agent or semantic views.

"What would it take to make this auditable for a regulated industry?"

  • Full query audit trail: CHAT_HISTORY + ACCESS_HISTORY (who queried what). Add query_id and generated SQL to history table.
  • Data lineage: Semantic views provide declarative lineage (SV → view → raw table). Add Snowflake Tags for classification.
  • Immutability: Time Travel + Fail-Safe on CHAT_HISTORY. No DELETE access for non-admin roles.
  • Model governance: Pin agent model version. Test before upgrading. VQRs serve as regression suite.
  • PII handling: Census data is aggregate (no PII at block group level). But for sensitive domains: apply dynamic data masking policies.
  • SOC 2 / HIPAA alignment: Snowflake's native encryption + no data egress + RBAC satisfies most framework controls. Agent stays inside the perimeter.
